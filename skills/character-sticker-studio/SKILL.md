# 十一表情包

把客户参考转化为可复核、可返修的表情素材。卖点是人物一致性、动作表达、细节检查和交付完整；不承诺一次生成完美、全自动免审或平台包过。

## 三项硬性验收标准

1. **画风固定**：新人物必须对照同一套已确认视觉样张，后续动作始终以本项目已确认人物母版为基准。文字风格描述不能代替视觉参考。更换人物、动作、会话或宿主不构成换画风的理由；缺参考或参考无法读取时标记待补齐，不凭空解释成另一画风。
2. **细节还原**：逐项记录并保留照片中可辨认及用户特别指定的面部特征、发型、服装和每件配饰。颜色、形状、数量、所属部位和佩戴位置都是约束；不能只做到“像戴了某种首饰”。看不清则核实，不能猜测后当成已经还原，也不擅自删除、换款或移位。
3. **位置与视角合理**：从人物身体部位追踪每件配饰，按正面、背面、侧面、动作和遮挡决定露出部分。掌心朝前通常只见戒圈背段；不能把装饰戒面画到掌心。被遮住与遗漏须分清，双手出现不等于两个戒面都要出现。

三项分别判定通过／待核实／需返修，任一未通过就不能把该图列为合格成品或继续复制同类错误。按[逐帧检查](references/quality-and-repair.md)留下具体依据，再更新visual_review；已有格式检查只能证明格式及复核记录有效，不能替代画面判断。修订指令本身不代表这三项已经实际达标。

## 客户只需照片和一句话

客户不需要另提供画风图。产品已内置获准使用的原24款样片和已确认细节样片；新项目按[内置样片绘图流程](references/generation-recipe.md)自动取图、打开并作为绘图工具的真实输入。优先运行 `node scripts/resolve-style.cjs` 检查取图位置和摘要。样片缺失或宿主无法引用时明确报告，不退回文字猜画风，也不使用被否定的虚构通用图。

首次使用、抱怨不好用或中断后接续，按[客户使用流程](references/customer-journey.md)执行。客户可以只说“帮我做一套自己的表情包”；Agent负责整理需求和处理技术步骤，不要求客户自己填写配置、写长提示词或先学会投稿。默认先满足个人聊天使用，只有明确要正式投稿才展开平台资料与配套。

新人物采用[固定画风](references/fixed-style.md)：自然舒展的半身、细腻手绘漫画线条、柔和明暗和克制的贴纸轮廓。固定的是画法；本人特征、衣服、首饰、场景、数量与文字按本次客户决定。先核对小样的相似度与画风，再扩展动作。不要把旧客户照片作为公共默认参考。

用户认可并要求固定时，按固定画风中的“确认与恢复”原样保存样张、文件摘要和确认依据；后续实际引用该图，不再重猜风格。开始新任务时检查项目的画风锁定记录；本机可选的私有索引仅在授权范围内补充参考，不能随公共Skill分发。

## 开始前只取必要上下文

读取当前项目的状态、角色规范和指定表情记录；续改时不重新寻找全部历史。遵循用户已确认的母版、数量、风格、文字与授权范围。客户已经认可母版就直接继续，不重复要求确认。

分清本轮是定稿角色、批量制作、局部返修还是导出投稿素材。用户只问哪个文件对应上传框时，直接按既有文件匹配，不触发重画。

先按 [运行环境与多端接续](references/runtime.md) 检查当前实际能力，再决定执行路径。本技能的共用流程适用于能读取 SKILL.md 的 Agent；不要把宿主名称、模型品牌或成功导入当成完整制作能力已验证。WorkBuddy、豆包工作与 Codex 的安装入口见 [宿主接入](references/hosts.md)。

绘制与视觉修正使用当前环境实际提供的图像生成／编辑工具，遵守其调用规则，不写死某一家工具名称。不假定买家有 API 密钥、额度或所有 MCP。缺少绘图工具时可用已提供的帧做导出；缺少执行环境时保存角色规范、帧图与待办并交接，明确尚未产出 GIF。不要拿文字说明、视频或静态图冒充已完成的透明循环 GIF。

## 角色与动作

- 按 [角色与动作](references/character-and-motion.md)建立项目内的角色规范，将已确认事实、实现假设、待验证细节分开。
- 提取真实脸部标志、发型、衣服及每件配饰的所属位置；没有参考依据时不添加痣、戒指或固定某根手指。
- 左右采用人物本人的解剖左右；镜像、手心／手背、遮挡都要记录。尤其注意掌心侧不应出现位于手背侧的宝石戒面。
- 未定稿时先做一个代表性人物样稿与一个真实动作循环；已经确认的不要从头再来。后续始终引用同一已确认母版，避免连续用衍生图当唯一身份参考而累积漂移。
- 数量服从用户和当前平台要求；动作要有区别，文字由用户决定。默认不把“无字、24张、绿色衣服、某个性别或配饰”当通用规则。
- 简单表情可以先试 3～6 张关键画面；复杂动作增加帧或简化动作。判断依据是实际播放效果，不是固定帧数。不能把统一晃动或只换文字当作全部动作。
- 透明四宫格可以用于分帧，但每格须独立且留足空隙。细节修正用图像编辑工具；脚本仅做分帧、裁切、缩放、编码、质检和打包。

## 制作与局部返修

按 [逐帧检查](references/quality-and-repair.md)检查原图及最终聊天尺寸。必须同时满足：
1. 内容／外观检查：身份、五官标志、手指结构、左右配饰、戒指正反面、单枚吊坠、轮廓与动作含义。
2. 格式检查：真实多帧、循环、尺寸、文件大小、透明与画布边缘。

导出成功只代表格式通过，不自动代表视觉通过。每条视觉记录绑定本次 GIF 的 SHA256；重新导出后旧记录不得直接沿用。暂不合格帧可排除并重编排，前提是剩余画面仍构成完整动作；记录取舍，不把未修好的原图说成已修好。

对同一局部问题连续两次修正仍失败时，先改变提示或手势实现、拆开复杂遮挡，再继续；若会改变已确认核心设计或超出约定返工预算，带上具体对比再询问。工具权限拒绝不得绕过。不得用无上限重试消耗客户额度。

## 确定性工具

需要初始化、导出、检查和打包时读取 [工具用法](references/tooling.md)：
- `node scripts/sticker-kit.cjs init --project <项目路径>`
- `node scripts/sticker-kit.cjs export --project <项目路径> --id <编号>`
- `node scripts/sticker-kit.cjs validate --project <项目路径>`
- `node scripts/sticker-kit.cjs package --project <项目路径>`

Node 与 sharp 是导出依赖，可先运行 `node scripts/runtime-check.cjs` 验证本次执行器的编码能力；这不检测绘图工具或证明完整宿主兼容。依照买家安装说明或当前宿主提供的依赖路径使用，不把本机路径写进 Skill，不自行全局安装软件。每次修订使用新的 revision，保留旧输出。客户原始照片仅留在客户项目。分发Skill不携带未获准分发的照片、肖像素材或私人文件路径；明确获准纳入包内的画风样片按其指定范围使用。

手机发起任务时，先确认任务运行在云端、已授权的远程电脑还是仅当前聊天中。切换入口必须沿用同一项目与已确认母版；需要转移文件时只转移本项目必要文件，并遵守用户授权，不假定文件和自定义技能会自动跨端同步。

工具当前实现动态 GIF；静态需求仍可用已生成的单图按平台规格导出，不能为凑工具要求伪造动画。脚本不调用绘图、不联网、不发送素材、不提交平台。

## 平台与交付

微信投稿读取 [微信规范快照](references/wechat-profile.md)，核验当前官方页面再使用；快照日期不是永久保证。用户要求发布前确认时，先说明具体不符处与建议，取得对应确认后再改数量、内容或分包。先前确认在本项目继续有效。

封面、面板图标和横幅分别准备。透明无描边封面不能直接用带白边的聊天表情代替。配套材料也要有视觉复核记录。

个人使用交付实际GIF／PNG、总览、离线预览、ZIP和微信使用指引；优先给用户能取回的文件。需要投稿时才加三项配套、含义词和投稿说明。技术检查与恢复记录放在项目中，不让客户先读完整检查报告才找到表情。记录“文件已生成、已交付、客户确认添加”各自状态，不把打包成功当作微信已添加。按当前任务授权保存；不默认上传、上架、展示为售卖案例、发送给第三方或替客户提交证件。文案里的作者、肖像授权和 AI 声明必须真实；公开宣传只声称已经验证的能力。

商业接单或买家询问授权、成本与支持时，读取 [商业边界](references/commercial-boundaries.md)。Skill 自身授权、客户肖像权、绘图服务条款和平台审核是四件不同的事。
